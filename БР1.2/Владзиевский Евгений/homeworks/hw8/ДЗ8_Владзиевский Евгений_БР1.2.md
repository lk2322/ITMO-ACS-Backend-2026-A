## 1. Цель работы

Реализовать автоматизированный пайплайн непрерывной интеграции и
непрерывной доставки компонентов микросервисного приложения в целевую
облачную инфраструктуру — кластер Kubernetes из ЛР7.

---

## 2. Почему пайплайн из ДЗ6 пришлось переделать

В ДЗ6 пайплайн разворачивал приложение через Docker Compose: синхронизировал
исходники на сервер, вызывал `docker compose build` и `up -d`, перечитывал
конфигурацию nginx. После перехода на Kubernetes (ЛР7) этот способ больше
не работает — Compose-стека на сервере нет, а приложением управляет кластер.

Изменения коснулись не только команд:

| Аспект | ДЗ6 (Docker Compose) | ДЗ8 (Kubernetes) |
|---|---|---|
| Что доставляется | исходники на сервер | образы в containerd кластера |
| Чем выкатывается | `docker compose up -d` | `kubectl apply -k` |
| Версия | `latest`, перезаписывается | тег по SHA коммита |
| Проверка кода | не выполнялась | отдельный CI-этап: vet, сборка, тесты |
| Откат | вручную | `kubectl rollout undo` при неудаче |
| Простой при выкатке | короткий, контейнер пересоздаётся | отсутствует: RollingUpdate + пробы |

Главная содержательная разница — не в инструменте, а в том, что в ДЗ6
пайплайн был только доставкой (CD), а в ДЗ8 появилась и интеграция (CI):
код проверяется до того, как попадёт на сервер.

## 3. Архитектура пайплайна

```
 push в ветку lab-8
         │
         ▼
 ┌──────────────────────── job: check ───────────────────────┐
 │ раннеры GitHub (ubuntu-latest), матрица из 6 сервисов     │
 │   go vet ./...   →   go build ./...   →   go test ./...   │
 └───────────────────────────┬───────────────────────────────┘
                             │ needs: check
                             ▼
 ┌──────────────────────── job: deploy ──────────────────────┐
 │ self-hosted runner на сервере (из ДЗ6)                    │
 │   сборка образов с тегом <SHA>                            │
 │   импорт в containerd k3s                                 │
 │   подстановка тега в kustomization                        │
 │   kubectl apply -k  →  rollout status  →  smoke-тест      │
 │   при неудаче: kubectl rollout undo                       │
 └───────────────────────────────────────────────────────────┘
```

Разделение по раннерам осознанное:

- **CI на раннерах GitHub.** Проверка кода не требует доступа к серверу,
  зато выигрывает от параллельности: шесть сервисов проверяются
  одновременно на шести машинах, а не по очереди на единственном
  self-hosted runner'е с четырьмя ядрами.
- **CD на self-hosted runner'е.** Кластер живёт в локальной сети без
  публичного адреса, поэтому выкатка возможна только изнутри периметра.
  Раннер уже установлен на сервере в ДЗ6 — ему доступны `docker`,
  `k3s ctr` и `kubectl`.

Параллельные выкатки запрещены через `concurrency`, чтобы два пайплайна
не правили кластер одновременно.

## 4. CI: проверка кода

```yaml
  check:
    name: Проверка кода (${{ matrix.service }})
    runs-on: ubuntu-latest
    strategy:
      fail-fast: false
      matrix:
        service: [api-gateway, auth-service, property-service,
                  booking-service, payment-service, messaging-service]
    steps:
      - uses: actions/checkout@v5
      - uses: actions/setup-go@v6
        with:
          go-version-file: '.../lab2/${{ matrix.service }}/go.mod'
          cache-dependency-path: '.../lab2/${{ matrix.service }}/go.sum'
      - run: go vet ./...
      - run: go build ./...
      - run: go test ./...
```

Решения:

- **`fail-fast: false`** — если падает один сервис, остальные всё равно
  проверяются: в отчёте о запуске видно сразу все проблемы, а не первую.
- **`go-version-file`** — версия Go берётся из `go.mod` сервиса, а не
  фиксируется в workflow: обновление модуля не требует правки пайплайна.
- **Кэш зависимостей** по `go.sum` ускоряет повторные запуски.

### 4.1 Тесты, которых не было

До этой работы в проекте не было ни одного теста, и этап `go test`
был бы формальностью. Добавлены юнит-тесты для двух мест auth-сервиса,
где ошибка означает дыру в безопасности:

| Тест | Что проверяет |
|---|---|
| `TestGenerateAndValidateToken` | выпущенный токен проходит проверку, claims сохраняются |
| `TestValidateTokenWrongSecret` | токен, подписанный другим ключом, отвергается |
| `TestValidateTokenExpired` | истёкший токен отвергается |
| `TestValidateTokenGarbage` | произвольная строка не принимается за токен |
| `TestHashAndCheckPassword` | хеш не равен паролю, верный пароль проходит, неверный — нет |
| `TestHashPasswordIsSalted` | два хеша одного пароля различаются (bcrypt солит) |

Это не полное покрытие, а минимум, который делает CI осмысленным:
регрессия в проверке подписи или в хешировании пароля теперь остановит
выкатку.

## 5. CD: сборка и выкатка в кластер

### 5.1 Теги образов

В ЛР7 образы собирались вручную с тегом `latest` — по кластеру нельзя
было понять, какая версия запущена. Пайплайн тегирует образы коротким
SHA коммита:

```yaml
      - name: Определение тега образов
        id: tag
        run: |
          TAG="${{ github.event.inputs.image_tag }}"
          [ -n "$TAG" ] || TAG="$(git rev-parse --short HEAD)"
          echo "tag=$TAG" >> "$GITHUB_OUTPUT"
```

`workflow_dispatch` принимает тег параметром: это позволяет вручную
выкатить любую ранее собранную версию, то есть откатиться на неё.

### 5.2 Доставка образов в кластер

Внешнего registry в учебном стенде нет, поэтому образы попадают в
containerd кластера напрямую:

```bash
sudo docker build -q -t "rental/${svc}:${TAG}" "${SRC_DIR}/${svc}"
sudo docker save "rental/${svc}:${TAG}" | sudo k3s ctr images import -
```

В промышленной конфигурации этот шаг заменяется на `docker push` в
приватный registry, а кластер тянет образ сам — тогда узлов может быть
много, и каждый получит образ без участия пайплайна.

### 5.3 Применение манифестов

Тег подставляется в блок `images` kustomization, после чего применяются
манифесты:

```bash
sed -i "s/newTag: .*/newTag: ${TAG}/" "${K8S_DIR}/kustomization.yaml"
kubectl apply -k "${K8S_DIR}"
```

Так выкатывается не только новый код, но и изменения манифестов:
правка лимитов или переменных окружения доезжает тем же пайплайном.

Готовность проверяется по каждому Deployment:

```bash
kubectl -n rental rollout status "deployment/${dep}" --timeout=180s
```

`rollout status` ждёт, пока новые поды пройдут пробы готовности. Если
образ сломан, команда завершится с ошибкой по таймауту — и пайплайн
перейдёт к откату.

### 5.4 Smoke-тест

После выкатки приложение проверяется снаружи, через Ingress:

| Проверка | Ожидание |
|---|---|
| `GET /health` | 200 (до 20 попыток с паузой) |
| `GET /api/v1/users/me` без токена | 401 |
| `POST /api/v1/auth/login` с неверным паролем | 401 или 400 |

Проверяется не только «отвечает ли», но и то, что авторизация работает:
сервис, запущенный с пустым JWT-ключом, ответил бы на эти запросы иначе.

## 6. Откат при неудаче

```yaml
      - name: Откат при неудаче
        if: failure() && steps.rollout.outcome != 'skipped'
        run: |
          for dep in auth-service property-service booking-service \
                     payment-service messaging-service api-gateway; do
            kubectl -n rental rollout undo "deployment/${dep}" || true
          done
```

Kubernetes хранит историю ревизий Deployment, поэтому откат — это
возврат к предыдущему ReplicaSet, а не повторная сборка старого кода.
Шаг срабатывает только если выкатка уже начиналась: падение на этапе
сборки образов откатывать нечего.

После отката пайплайн ещё раз запрашивает `/health` и печатает
результат — чтобы в логе было видно, вернулось ли приложение в рабочее
состояние.

### 7.2 Запуск 2: ручная выкатка заданного тега

`workflow_dispatch` с параметром `image_tag` отработал успешно — это

### 7.3 Запуск 3: проверка отката

Чтобы проверить откат, в манифест auth-service был закоммичен неверный
`DB_HOST` (`auth-db-wrong-host`). Сервис при старте не может подключиться
к базе и завершается с `log.Fatal`, то есть под никогда не станет
готовым.

Ожидаемая цепочка сработала полностью:

```
✓ Применение манифестов
✗ Ожидание выкатки
    Waiting for deployment "auth-service" rollout to finish:
    1 old replicas are pending termination...
    error: timed out waiting for the condition
- Smoke-тест через Ingress  (пропущен)
✓ Откат при неудаче
```

Состояние после отката:

```
$ kubectl -n rental get deployment auth-service \
    -o jsonpath='{...env[?(@.name=="DB_HOST")].value}'
auth-db                     # неверное значение откачено

$ kubectl -n rental get pods -l app=auth-service
auth-service-6c6fc77bf5-v7978   1/1   Running   0   5m39s
```

**Приложение при этом не прерывалось.** Проверки снаружи во время
сломанной выкатки и после неё:

```
health=200
login(неверный пароль)=401
```

Причина — `maxUnavailable: 0` в стратегии RollingUpdate: Kubernetes не
снимает старый под, пока новый не пройдёт пробу готовности. Сломанная
версия просто не получила трафик.

Важная деталь, которую стоит зафиксировать честно: `rollout undo`
возвращает **предыдущую ревизию**, а не «последнюю заведомо рабочую».
В этом запуске предыдущей ревизией оказалась выкатка из запуска 2
(с тегом `broken-tag-test`), и кластер вернулся именно к ней. Если бы
две неудачные выкатки шли подряд, откат вернул бы первую из них.
Решение — хранить тег последней успешной сборки и откатываться на него
явно; в текущем пайплайне этого нет.

## 8. Заключение

Реализован пайплайн непрерывной интеграции и доставки приложения в
кластер Kubernetes. Он состоит из двух этапов: проверки кода на раннерах
GitHub (матрица из шести сервисов: `go vet`, сборка, тесты) и выкатки в
кластер на self-hosted runner'е (сборка образов с тегом по SHA, импорт в
containerd, `kubectl apply -k`, ожидание готовности, smoke-тест, откат
при неудаче).

### Что изменилось по сравнению с ДЗ6

- появился этап CI: код проверяется до выкатки, а не после;
- образы тегируются SHA коммита вместо `latest` — видно, какая версия
  работает в кластере, и возможен откат на конкретную сборку;
- выкатка идёт без простоя за счёт RollingUpdate и проб готовности;
- при неудачной выкатке пайплайн сам возвращает предыдущую ревизию.

### Ограничения

- **Нет registry.** Образы импортируются в containerd узла, поэтому
  пайплайн работает только с одноузловым кластером. В многоузловом нужен
  приватный registry, откуда образы тянет каждый узел.
- **Один runner.** Self-hosted runner единственный, и выкатки идут по
  очереди (`concurrency`). Для параллельных окружений потребуется
  отдельный раннер на каждое.
- **Откат только приложения.** `rollout undo` возвращает образы и
  параметры подов, но не откатывает миграции схемы БД: несовместимая
  миграция потребует ручного вмешательства.
- **Откат на предыдущую ревизию, а не на последнюю рабочую.** Это
  выяснилось при проверке (раздел 7.3): если неудачные выкатки идут
  подряд, откат вернёт предыдущую неудачную. Правильнее хранить тег
  последней успешной сборки и выкатывать его явно.
- **Покрытие тестами минимальное.** Проверены JWT и хеширование паролей;
  бизнес-логика сервисов и HTTP-слой тестами не покрыты.

### Что дальше

Естественное продолжение — разделение окружений (stage и production с
ручным подтверждением выкатки через GitHub Environments), публикация
образов в registry и добавление интеграционных тестов, поднимающих
сервис вместе с временной базой.
