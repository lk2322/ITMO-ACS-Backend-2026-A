## 1. Цель работы

Задокументировать микросервисное приложение средствами Postman,
OpenAPI/Swagger и MkDocs.

Документация делалась не «по памяти», а сверялась с работающим
приложением в кластере: каждый описанный эндпоинт вызывался, и ответы
сверялись с тем, что написано в спецификации. Такой подход оказался
продуктивным — он выявил дефект конфигурации и несколько
недокументированных бизнес-правил (раздел 6).

---

## 2. Три инструмента и их роли

Инструменты не дублируют друг друга, у каждого своя задача:

| Инструмент | Что описывает | Кто читатель |
|---|---|---|
| **OpenAPI** | формальный контракт: пути, параметры, схемы тел, коды ответов | разработчик клиента, генератор кода, Swagger UI |
| **Postman** | исполняемый сценарий работы с API с проверками | тестировщик, новый разработчик, CI |
| **MkDocs** | связный рассказ: архитектура, развёртывание, эксплуатация | вся команда, преподаватель, будущий я |

OpenAPI отвечает на вопрос «какие есть методы и что они принимают»,
Postman — «как этим пользоваться в правильном порядке», MkDocs — «как всё
устроено и что делать, когда сломалось».

## 3. OpenAPI: контракт API

Файл [`openapi/openapi.yaml`](openapi/openapi.yaml) — спецификация
OpenAPI 3.0.3 на публичный контракт API Gateway.

| Показатель | Значение |
|---|---|
| Путей | 20 |
| Операций | 30 |
| Схем данных | 12 |
| Тегов (разделов) | 7 |

### 3.1 Структура

```yaml
info:        название, версия, описание ролей
servers:     кластер k3s и локальный Docker Compose
tags:        Аутентификация, Справочники, Объекты, Аренда,
             Сообщения, Транзакции, Служебное
paths:       20 путей
components:
  securitySchemes:  bearerAuth (JWT)
  parameters:       IdParam — переиспользуемый параметр пути
  responses:        ValidationError, Unauthorized, Forbidden, NotFound
  schemas:          User, Property, Rental, Transaction, Message, …
security:    bearerAuth по умолчанию для всех методов
```

Повторяющиеся ответы вынесены в `components/responses`: описание ошибки
`401` задано один раз и переиспользуется двадцатью операциями. Методы,
не требующие токена (`/health`, регистрация, вход), переопределяют
глобальную схему через `security: []`.

### 3.2 Описан не только «счастливый путь»

Для каждой операции перечислены реальные коды ошибок с условиями: `403`
для роли без прав, `409` при пересечении дат бронирования, `413` при
превышении размера фотографии. Описаны и ограничения, которые видны
только в коде: допустимые переходы статусов аренды, предусловие оплаты,
правило доступа к переписке.

### 3.3 Проверка спецификации

Спецификация проверена структурным валидатором: разрешимость всех
`$ref`, наличие `responses` у каждой операции, объявление всех
параметров пути, существование используемых схем авторизации.

```console
$ python3 validate_openapi.py openapi/openapi.yaml
путей: 20, операций: 30, схем данных: 12
предупреждений: 0
ошибок нет
```

## 4. Postman: исполняемая документация

Коллекция [`postman/Rental_API_K8s.postman_collection.json`](postman/Rental_API_K8s.postman_collection.json)
и окружение `Rental_API_K8s.postman_environment.json`.

| Показатель | Значение |
|---|---|
| Папок (разделов сценария) | 8 |
| Запросов | 29 |
| Проверок `pm.test` | 76 |

### 4.1 Сценарий

```
0. Доступность          /health
1. Регистрация и вход   владелец, арендатор, повторный email, неверный
                        пароль, профиль, профиль без токена
2. Справочники          типы недвижимости, удобства
3. Публикация объекта   создание владельцем; отказ арендатору (403);
                        отказ при неполном теле (400); карточка
4. Поиск                все объекты, фильтр по городу, фильтр по цене
5. Бронирование         бронь, конфликт дат (409), карточка,
                        подтверждение владельцем, оплата
6. Переписка            сообщение, ответ, список диалогов, история
7. История              мои аренды, оплаченные, транзакции
```

### 4.2 Что проверяется

Не только коды ответов. Примеры проверок:

```javascript
pm.test("объект принадлежит владельцу", () => {
    pm.expect(pm.response.json().owner_id)
      .to.eql(Number(pm.collectionVariables.get("owner_id")));
});

pm.test("все найденные — из нужного города", () => {
    const city = pm.collectionVariables.get("search_city");
    pm.response.json().items.forEach(p => pm.expect(p.city).to.eql(city));
});

pm.test("цены в заданном диапазоне", () => {
    pm.response.json().items.forEach(p => {
        pm.expect(p.price_per_day).to.be.at.least(1000);
        pm.expect(p.price_per_day).to.be.at.most(10000);
    });
});
```

Коллекция самодостаточна: адреса почты генерируются из метки времени
(иначе повторный прогон упёрся бы в уникальность email), даты
бронирования считаются от текущей, идентификаторы передаются между
запросами через переменные коллекции.

## 5. MkDocs: сайт документации

Каталог [`mkdocs/`](mkdocs/) — исходники сайта на MkDocs с темой
Material.

| Страница | Содержание |
|---|---|
| Обзор | что за система, стек, быстрый старт, роли |
| Архитектура | состав сервисов, база на сервис, схемы проверки токенов, события Kafka, сага оплаты |
| Справочник API | встроенный Swagger UI поверх `openapi.yaml`, общие правила и формат ошибок |
| Тестирование в Postman | импорт коллекции, состав сценария, запуск через newman |
| Развёртывание | история от Compose до Kubernetes, текущая схема, ручное развёртывание |
| Мониторинг | стек ЛР6, дашборд, готовые запросы PromQL и LogQL |
| Эксплуатация | диагностика, типовые поломки, откат, работа с Kafka и БД |

### 5.1 Сборка и публикация

Сайт собирается в статику и раздаётся nginx:

```dockerfile
FROM squidfunk/mkdocs-material:9.5.44 AS build
WORKDIR /docs
COPY mkdocs/mkdocs.yml ./mkdocs.yml
COPY mkdocs/docs ./docs
# спецификация попадает в сайт: Swagger UI тянет её с того же адреса
COPY openapi/openapi.yaml ./docs/openapi.yaml
RUN mkdocs build --strict --site-dir /site

FROM nginx:alpine
COPY --from=build /site /usr/share/nginx/html
```

Флаг `--strict` превращает предупреждения MkDocs (битые ссылки,
страницы вне навигации) в ошибки сборки — документация с битой ссылкой
просто не соберётся.

Сайт развёрнут в том же кластере отдельным Deployment и доступен через
общий Ingress: **http://192.168.1.245/docs/**. Сборка и выкатка
добавлены в пайплайн ДЗ8: изменение файлов документации публикует новую
версию сайта автоматически.

## 6. Что документирование нашло в приложении

Самое полезное в этой работе — не сами файлы, а дефекты, которые
всплыли при сверке документации с реальностью.

### 6.1 Дефект конфигурации: сервисы отвергали валидные токены

При первом прогоне коллекции три эндпоинта возвращали `401` с валидным
токеном, хотя `/users/me` с тем же токеном работал:

```
/api/v1/users/me          200
/api/v1/property-types    401
/api/v1/amenities         401
/api/v1/transactions      401
```

Причина: `property-service` и `payment-service` проверяют подпись JWT
самостоятельно, ключ берут из `JWT_SECRET`, а при отсутствии переменной
подставляют значение по умолчанию из кода. В production-конфигурации
`JWT_SECRET` передавался только `auth-service`, `messaging-service` и
`api-gateway` — остальные сверяли подпись не тем ключом.

Ошибка появилась ещё в ЛР4 (там генерируется случайный секрет) и
переехала в манифесты Kubernetes. Smoke-тесты её не ловили: они
проверяли `/health`, регистрацию и `GET /properties`, который на уровне
сервиса не требует авторизации.

Исправление — передать `JWT_SECRET` обоим сервисам — внесено и в
манифесты ЛР7, и в compose ЛР4, после чего все эндпоинты отвечают
корректно.

### 6.2 Недокументированные бизнес-правила

| Правило | Как проявилось |
|---|---|
| Оплатить можно только подтверждённую бронь | `POST /rentals/{id}/pay` в статусе `pending` → `400 rental cannot be paid in status pending, expected confirmed` |
| Переписка доступна только участникам аренды в статусе `confirmed`, `paid` или `payment_pending` | `POST /messages` при брони `pending` → `403 sender is not participating in rental of this property` |
| Переходы статусов аренды ограничены таблицей | попытка неразрешённого перехода → `400 invalid status transition` |

Ни одно из этих правил не было описано нигде, кроме кода. Все три
внесены в спецификацию, а в сценарий Postman добавлен недостающий шаг
«владелец подтверждает бронь».

### 6.3 Редирект при создании объекта

`POST /api/v1/properties` отвечает `307` и переносит запрос на
`/api/v1/properties/` — следствие вложенной группы маршрутов в шлюзе.
Клиенты, следующие редиректам, работают прозрачно, но для написания
своего клиента это стоит знать, поэтому поведение описано в
спецификации.

### 6.4 Побочная находка: SHA из одних цифр ломал выкатку

Не относится к документации напрямую, но обнаружено при выкатке
исправления. Пайплайн ДЗ8 подставлял короткий SHA в `newTag`
kustomization без кавычек. Коммит `5670863` состоит только из цифр,
YAML разобрал его как число, и выкатка упала:

```
error: invalid Kustomization: json: cannot unmarshal number
into Go struct field Image.images.newTag of type string
```

Предыдущие SHA (`c4388eb`, `5e11e90`) содержали буквы, поэтому ошибка
не проявлялась. Исправлено — тег подставляется в кавычках.

## 7. Проверка

### 7.1 Спецификация

```console
$ python3 validate_openapi.py openapi/openapi.yaml
путей: 20, операций: 30, схем данных: 12
предупреждений: 0
ошибок нет
```

Проверяются разрешимость всех `$ref`, наличие `responses` у каждой
операции, объявление каждого параметра пути (включая заданные через
`$ref` на компонент) и существование используемых схем авторизации.

### 7.4 Две поломки, найденные при публикации

**Сайт отдавал 404 на всех страницах.** Ingress передаёт путь вместе с
префиксом `/docs`, а статика лежала в корне nginx — сервер искал
`/docs/index.html` и не находил. Решение: класть собранный сайт в
подкаталог `docs` внутри образа.

**Smoke-тест пайплайна поймал 502.** Проверка «вход с неверным паролем»
выполнялась сразу после пересоздания подов шлюза и попала в тот самый
промежуток, когда под уже завершается, но ещё не исключён из
эндпоинтов — ровно та недоработка, которая была зафиксирована в отчёте
ЛР7. Устранены обе стороны проблемы:

- в манифесты добавлен `preStop`-хук с паузой, чтобы под переставал
  получать трафик раньше, чем закрывает соединения;
- проверки smoke-теста сделаны повторяемыми, а в сам тест добавлена
  проверка доступности `/docs/`.

После исправлений пайплайн отработал зелёным, и сайт документации
выкатывается вместе с приложением.

## 8. Заключение

Приложение задокументировано тремя взаимодополняющими способами:
формальный контракт в OpenAPI (20 путей, 30 операций, 12 схем),
исполняемый сценарий в Postman (29 запросов, 76 проверок) и сайт
документации на MkDocs, опубликованный в том же кластере и собираемый
пайплайном из ДЗ8.

Главный результат — не объём документации, а то, что сверка описания с
работающей системой нашла дефекты, которые не ловили ни тесты, ни
smoke-проверки предыдущих работ:

- `property-service` и `payment-service` отвергали валидные токены из-за
  неподанной переменной `JWT_SECRET` — дефект жил с ЛР4;
- три бизнес-правила существовали только в коде (предусловие оплаты,
  правило доступа к переписке, таблица переходов статусов);
- пайплайн падал на коммите с SHA из одних цифр;
- выкатка оставляла окно, в котором один запрос мог получить 502 — это
  было видно ещё в ЛР7, а теперь закрыто `preStop`-хуком.

### Чем отличается рабочая документация от формальной

- **Описаны не только успешные ответы.** Для каждой операции указано,
  когда она вернёт 400, 401, 403, 404, 409 — и почему.
- **Описаны предусловия.** «Оплатить аренду» бесполезно знать без
  правила «сначала владелец подтверждает бронь».
- **Документация исполняема.** Коллекция Postman — не картинка, её можно
  запустить и получить 29 зелёных проверок или понять, что сломалось.
- **Документация собирается с `--strict`.** Битая ссылка не доезжает до
  сайта, потому что ломает сборку.

### Что можно улучшить

- **Генерация спецификации из кода.** Сейчас `openapi.yaml` написан
  вручную и может разойтись с реализацией. Аннотации `swaggo` в
  обработчиках сделали бы спецификацию побочным продуктом сборки.
- **Проверка контракта в CI.** Schemathesis или Dredd гоняют запросы
  по спецификации и ловят расхождения автоматически.
- **Запуск коллекции в пайплайне.** `newman run` после выкатки заменил
  бы нынешний минимальный smoke-тест полноценным сценарием.
- **Версионирование документации.** При появлении `/api/v2` понадобится
  `mike` для нескольких версий сайта одновременно.
