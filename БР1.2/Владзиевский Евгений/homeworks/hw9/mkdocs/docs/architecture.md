# Архитектура

## Состав системы

```
                         Ingress (Traefik)
                                │
                        ┌───────▼────────┐
                        │  API Gateway   │  проверка JWT, маршрутизация
                        └──┬──┬──┬──┬──┬─┘
             ┌─────────────┘  │  │  │  └──────────────┐
             ▼                ▼  ▼  ▼                 ▼
      ┌────────────┐  ┌────────────┐  ┌────────────┐  ┌──────────────┐
      │    auth    │  │  property  │  │  booking   │  │  messaging   │
      └─────┬──────┘  └─────┬──────┘  └─────┬──────┘  └──────┬───────┘
            │               │               │ ◄──────┐       │
            ▼               ▼               ▼        │       ▼
         auth-db       property-db      booking-db   │   messaging-db
                                                 ┌───┴──────┐
                                                 │ payment  │
                                                 └────┬─────┘
                                                      ▼
                                                  payment-db
                              Kafka — события между сервисами
```

## Сервисы

| Сервис | Порт | Зона ответственности |
|---|---|---|
| `api-gateway` | 8080 | единственная публичная точка входа, проверка JWT и ролей, проксирование |
| `auth-service` | 8081 | регистрация, вход, профили, выпуск и проверка токенов |
| `property-service` | 8082 | каталог объектов, справочники, фотографии |
| `booking-service` | 8083 | бронирования, оркестрация саги оплаты |
| `payment-service` | 8084 | платежи и транзакции |
| `messaging-service` | 8085 | переписка по объектам |

## База на сервис

Каждый сервис владеет своей базой и не ходит в чужие напрямую. Данные
других доменов запрашиваются по HTTP (например, booking спрашивает у
property цену объекта) или приходят событиями через Kafka.

Плата за такой подход — отсутствие внешних ключей между доменами и
необходимость согласовывать данные приложением. Выигрыш — сервисы можно
разворачивать и менять независимо.

## Проверка токенов: две схемы

Разные сервисы проверяют JWT по-разному, и это важно при настройке
окружения:

| Сервис | Как проверяет | Что нужно в окружении |
|---|---|---|
| `api-gateway`, `auth-service` | локально, по общему ключу | `JWT_SECRET` |
| `property-service`, `payment-service`, `messaging-service` | локально, по общему ключу | `JWT_SECRET` |
| `booking-service` | HTTP-запрос в auth-service | `AUTH_SERVICE_URL`, `SERVICE_TOKEN` |

!!! warning "Частая ошибка конфигурации"
    Если сервису, проверяющему токен локально, не передать `JWT_SECRET`,
    он возьмёт значение по умолчанию из кода. Токены, подписанные
    auth-service настоящим ключом, начнут отвергаться — запросы к этому
    сервису будут возвращать `401`, хотя тот же токен работает на других
    эндпоинтах. Именно так выглядела ошибка в `property-service` и
    `payment-service` до её исправления.

## Асинхронные события

События публикуются через **Transactional Outbox**: сервис в одной
транзакции пишет и бизнес-данные, и запись в таблицу `outbox_events`,
а отдельный воркер отправляет её в Kafka и помечает опубликованной.
Так событие не теряется, если Kafka временно недоступна.

| Топик | Кто пишет | Пример события |
|---|---|---|
| `user.events` | auth-service | `user.registered` |
| `property.events` | property-service | `property.created` |
| `rental.events` | booking-service | `rental.status_changed` |
| `payment.events` | payment-service | `payment.completed` |

## Сага оплаты

```
tenant → POST /rentals/{id}/pay
            │
            ├─ booking-service проверяет аренду и права
            ├─ HTTP → payment-service: создать платёж (idempotency_key)
            ├─ успех → аренда переводится в статус paid
            └─ событие rental.status_changed в outbox → Kafka
```

`idempotency_key` защищает от двойного списания: повторный запрос с тем
же ключом вернёт ранее созданную транзакцию, а не создаст новую.
